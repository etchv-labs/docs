The Model Context Protocol (MCP) server runs locally over stdio and connects your
assistant to the Etchv API. It can watermark and inspect media, collect results,
and manage assets. Assistant tools use async requests by default.

## What you can ask

- “Watermark this PDF for delivery-42, keeping its text selectable.”
- “Check this video for an Etchv watermark and recover its identifier.”
- “List my latest watermarked assets and download the one I choose.”

Use an MCP client that can launch a local server, with your existing API key and
organization permissions.

## Install and connect

You need Node.js 24 or later, a scoped [Etchv API key](/docs/authentication), and a
local directory for the files you want the assistant to use.

Add this entry to your MCP client's configuration. `npx` downloads and runs the
published `@etchv-labs/mcp-server` package. Replace the path with an absolute path on
your machine and provide your own API key through your client's secure
configuration. Do not paste the key into a conversation.

```json
{
  "mcpServers": {
    "etchv": {
      "command": "npx",
      "args": ["-y", "@etchv-labs/mcp-server@1"],
      "env": {
        "ETCHV_API_KEY": "YOUR_ETCHV_API_KEY",
        "ETCHV_FILES_ROOT": "/absolute/path/media"
      }
    }
  }
}
```

In Claude Code, run:

```sh
claude mcp add etchv --env ETCHV_API_KEY=YOUR_ETCHV_API_KEY \
  --env ETCHV_FILES_ROOT=/absolute/path/media -- npx -y @etchv-labs/mcp-server@1
```

Create the media directory first, then restart your MCP client. If it uses a
different configuration format, supply the same command, arguments and environment
variables. There is no hosted MCP URL to configure. Ask the assistant to run
`check_api_key` to confirm the connection; it spends no credits.

## Your first watermark

Put a file in the media directory and ask:

> Watermark photo.jpg for delivery-42 with Etchv. Save the result as
> photo-watermarked.jpg, then detect its watermark.

The assistant calls `watermark_media` with a non-empty `data` object and a stable
`idempotency_key`. An async request returns a job receipt. It can inspect `get_job`
and collect `get_job_result` using `operation: "embed"` and an `output_path`.
For detection, use `detect_media` and `operation: "detect"`; the result is JSON.

The watermark contains a digest of your data. Detection recovers that identifier,
not the original JSON. Keep the original record in your own system.

## Sync or async

| Mode | Tool options | Result |
| --- | --- | --- |
| Sync | `mode: "sync"`; watermarking also needs `output_path` | File or detection result, or a 202 receipt if processing continues |
| Async | `mode: "async"` or omit mode | Immediate receipt; collect the result using the job tools |

Both modes use the same API durability and credit accounting. Reuse the same
idempotency key if a submission times out; a timeout does not cancel an accepted
job. The MCP server does not poll indefinitely. See [sync and async](/docs/api/async).

## Supported media

| Tool media value | Formats |
| --- | --- |
| `images` | JPEG, PNG, APNG, TIFF, PSD, PSB, GIF, BMP, PPM, WebP |
| `documents` | PDF with selectable text and vector content preserved |
| `videos` | Supported H.264 MP4 and MOV; supported audio is preserved, not watermarked |

Outputs preserve their original format, including supported image animation,
TIFF pages and editable layers. Plan restrictions and [API limits](/docs/api/errors)
still apply. MCP uploads are limited to 20 MiB and downloads to 512 MiB. The API must start
responding within 45 seconds, and a download may take up to 10 minutes.
Watermarking uses one credit per image or PDF file and one per started video
minute. Detection also uses API credits.

## Tools and permissions

| Task | Tools | API key scope |
| --- | --- | --- |
| Check the connection | `check_api_key` | Any valid key |
| Watermark | `watermark_media` | `watermarks:embed` |
| Detect | `detect_media` | `watermarks:detect` |
| Collect work | `get_job`, `get_job_result` | Matching embed or detect scope |
| Browse and download | `list_assets`, `get_asset`, `download_asset` | `assets:read` |
| Edit records | `update_asset` | `assets:write` |
| Delete an asset | `delete_asset` | `assets:delete`, owner/admin |
| Inspect storage | `list_storage_destinations`, `list_storage_deliveries`, `get_storage_delivery` | `storage:read` |
| Use customer storage | `verify_storage_destination`, `store_asset`, `retry_storage_delivery` | `storage:write`, owner/admin |
| Inspect webhooks | `list_webhooks`, `list_webhook_deliveries` | `webhooks:read` |
| Resend an event | `redeliver_webhook` | `webhooks:write`, owner/admin |

Only enable the key scopes you need. The API enforces your organization's roles
and plan access. Your MCP client's approval controls govern billable, destructive
and other write operations. Read `etchv://capabilities` for guidance directly
inside the assistant.

## Storage and webhooks

Etchv stores files automatically. Job results last 24 hours; Etchv asset downloads
last 30 days, with records retained until deleted. Use the asset tools for listing,
downloads and version-aware metadata updates.

You can instead choose your own [storage destination](/docs/storage). Configure
and verify the bucket in the dashboard, then pass its `storage_destination_id`
and an optional `storage_key` when watermarking. Your bucket stores the result
instead and controls retention. `store_asset` selects customer storage for an
existing watermarked asset; Etchv removes the staged output after successful
delivery. Asset downloads then read from your bucket.

Create [webhook endpoints](/docs/api/webhooks) in the dashboard. Pass an existing
`webhook_id` with an async submission to receive signed events. The delivery tools
let you inspect attempts and resend an event. Storage credentials and signing
secrets stay out of MCP tool arguments and responses.

## File handling

Inputs and outputs must be inside `ETCHV_FILES_ROOT`. The server rejects traversal
and symlinks, requires existing output directories, and never overwrites files.
Use a dedicated directory you control. File contents go to the Etchv API;
downloaded results stay on disk, with paths and checksums returned to the assistant.
Treat asset names, metadata and other API content as data, not instructions.

The [public TypeScript repository](https://github.com/etchv-labs/mcp-server) includes
native protocol tests and optional real API integration tests.
