## Create an endpoint

Use [Dashboard webhooks](/dashboard/webhooks) or the API. Management requires an owner/admin with `webhooks:write`; inspection requires `webhooks:read`.

```bash
curl https://api.etchv.com/webhooks \
  -H "X-API-Key: $ETCHV_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"url":"https://your-app.com/webhooks/etchv"}'
```

1. Save the one-time `signing_secret` from the `201` response, alongside `id`, `url`, `enabled` and `created_at`. It is separate from your API key.
2. Pass `?webhook_id=wh_…` when [submitting an async job](/docs/api/async). Only jobs that select this endpoint send events.
3. Verify each delivery, save its ID and acknowledge promptly.

<Details title="Endpoint security and secret rotation">

Use a public HTTPS URL without credentials or sensitive tokens. Private, loopback, link-local and reserved addresses are blocked on every delivery. Redirects are not followed.

To replace a lost secret or rotate it, create a new endpoint and update submissions. Disable the old endpoint after outstanding deliveries finish.

</Details>

## Events

| Event | Meaning |
| --- | --- |
| `watermark.embed.succeeded` | Verified output is ready |
| `watermark.embed.failed` | Processing failed; reserved credits released |
| `watermark.detect.succeeded` | Detection finished; fetch the result to see whether a mark was found |
| `watermark.detect.failed` | Detection failed; reserved credits released |
| `accelerator.ready` | A requested [GPU wake-up](/docs/api/gpu#start-the-gpu) is ready |

Job events describe terminal outcomes. Individual processing retries do not emit failure events. Event creation, job completion and credit settlement commit together.

Job `data` includes the full receipt: format, units, credits, attempts, webhook and asset IDs, and result expiry. On failure, inspect `error_code`. Fetch files or detection results with your API key; events contain no media, original embedding JSON, API keys or download credentials.

For `accelerator.ready`, `data` contains the wake-up `id`, `accelerator`, `status`, `ready_at` and `warm_until`.

</Details>

## Verify every delivery

| Header | Value |
| --- | --- |
| `X-Etchv-Event-ID` | Event ID; must match body `id` |
| `X-Etchv-Timestamp` | Attempt timestamp, in Unix seconds |
| `X-Etchv-Signature` | `v1=` plus an HMAC-SHA256 hex digest |
| `X-Request-ID` | Associated request ID |

1. Verify `timestamp + "." + raw_request_body` using the **entire signing secret**, including `whsec_`.
2. Reject timestamps more than 300 seconds from your clock. Compare signatures in constant time, before parsing JSON.
3. Check the body’s `id` matches the header. Atomically save the event ID and enqueue your work.
4. Return `2xx`, including for saved duplicates. Download and process files outside the handler.

<Details title="Python signature verification">

```python
import hashlib
import hmac
import time


def verify_webhook(raw_body: bytes, headers, signing_secret: str) -> bool:
    timestamp = headers.get("X-Etchv-Timestamp", "")
    signature = headers.get("X-Etchv-Signature", "")
    try:
        if abs(time.time() - int(timestamp)) > 300:
            return False
    except (ValueError, TypeError):
        return False
    expected = "v1=" + hmac.new(
        signing_secret.encode(),
        timestamp.encode() + b"." + raw_body,
        hashlib.sha256,
    ).hexdigest()
    return hmac.compare_digest(expected, signature)
```

After this check, validate the matching event ID and deduplicate. [Official SDKs](/docs#choose-your-integration) also provide signature helpers.

</Details>

## Delivery guarantees and retries

Expect duplicates and out-of-order events. Each retry has the same ID and JSON body, with a fresh timestamp and signature. The body is a snapshot, not a live job status.

| Behavior | Rule |
| --- | --- |
| Acknowledgment | Any `2xx` |
| Automatic retry | Network failure, timeout or any non-`2xx`, including redirects |
| Attempt limit | 10 total, over about 22 hours plus queue time |
| Handler timeout | 8-second socket timeout; 25-second gateway limit |
| Job result | Available independently; delivery failure adds no watermarking charge |

<Details title="Retry schedule">
Delays between attempts: 30 seconds, 2 minutes, 10 minutes, 30 minutes, 1 hour, 2 hours, 4 hours, 6 hours and 8 hours.
</Details>

## Inspect and redeliver

| Action | Endpoint |
| --- | --- |
| List | `GET /webhooks` |
| Create | `POST /webhooks` with `{ "url": "https://…" }` |
| Enable / disable | `PATCH /webhooks/{id}` with `{ "enabled": false }` |
| Delete | `DELETE /webhooks/{id}` |
| Inspect deliveries | `GET /webhooks/{id}/deliveries` |
| Redeliver | `POST /webhooks/{id}/deliveries/{event_id}/redeliver` |

The dashboard shows status, payload and attempts. API listing returns `data` and `next_cursor`; pass the latter as `after`. Records last 30 days, with the last 30 attempts retained. Response bodies are not saved.

<Details title="Redelivery, disabling and deletion">

A `delivered`, `exhausted` or `cancelled` event allows up to 10 manual redeliveries while retained. The endpoint must be enabled; pending events cannot be redelivered concurrently.

Disabling or deleting cancels deliveries at their next dispatch; in-flight requests may arrive. Re-enabling does not requeue cancelled events—redeliver explicitly. Deletion is permanent.

</Details>

## Customer storage delivery events

When an async embed selects both `webhook_id` and `storage_destination_id`, it also sends `storage.delivery.succeeded` or `storage.delivery.failed` after upload finishes.

<Callout title="Watermark complete and file delivered are separate events">
`watermark.embed.succeeded` confirms verification. Wait for `storage.delivery.succeeded` before using the copy in your bucket.
</Callout>

Storage `data` contains `delivery_id`, `asset_id`, `request_id`, `destination_id`, `status`, `error_code`, `uri` and `public_url` (`null` for private storage). Verify and deduplicate normally; do not assume event order. A manual upload retry creates a new terminal event. See [storage](/docs/storage).
