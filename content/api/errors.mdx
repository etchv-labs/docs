Non-success responses normally contain JSON with a `detail` field. Save the
HTTP status and any `X-Request-ID` header when investigating a failed request.

## Status codes

| Status | Meaning | Next step |
| --- | --- | --- |
| `401` | Missing or invalid authentication | Check your API key |
| `403` | Insufficient scope or access | Check key scopes and organization membership |
| `402` | Billing or credits unavailable | Check the organization's plan and credit balance |
| `409` | Conflicting input, duplicate operation or stale asset version | Inspect the operation, or reload the asset before editing |
| `404` | Asset not found or outside your organization | Check the asset ID and organization |
| `410` | Job result or asset file expired/deleted | The file is no longer available; its retained asset record remains readable |
| `413` | Image exceeds a size limit | Reduce the upload size or pixel dimensions |
| `422` | Invalid input or failed watermark verification | Check image encoding and JSON data; try another source image if verification failed |
| `503` | A required service is unavailable | Check service status and handle the failure in your application |

## Image limits

Uploads and delivered files must be at most **20 MB**. Images may contain up to
**32 frames or pages** (including an APNG default/poster image), totaling **40 megapixels** across all frames/pages.
**GIF frames are limited to one megapixel each**.
PSD/PSB are limited to **4 megapixels per canvas**, **64 layers**, and **16 megapixels
across layers**, including the two full-canvas watermark layers added by embedding.
The dashboard upload limit is **4 MB**. Native formats that browsers cannot preview
can still be uploaded. Embedding preserves the original format.
High-bit-depth and CMYK variants are not supported in this release.
Send encoded image bytes rather than a URL or base64 string. The `data` field
must contain a non-empty JSON object, not an array or plain string.

## Credits and retries

Successful embed and detect operations each consume one credit. Embedding reserves
one credit when its durable job is accepted, charges on verified persisted success,
and releases the reservation on terminal failure. Retries and result downloads do
not consume additional credits. During an outage, reservations remain until a worker
can complete or finalize the job.

Embedding SDK calls automatically retry transient failures and poll `202` jobs.
A client timeout does not cancel the job. Resume with the request ID or resubmit the
same image/data and idempotency key. Terminal JSON has `status: "failed"`; retrying
that key returns the same failure. See [embedding](/docs/api/embed) for retention.

The standard image and PDF detection endpoints are synchronous (their `/async` alternatives use durable jobs): SDKs do not retry those detections
automatically. Video detection uses durable jobs and automatic polling. Images and
PDFs use one credit per operation; video uses one credit per started minute, per
operation. Asset management and downloads consume no credits.

## Service status

Check [status.etchv.com](https://status.etchv.com) for service availability.
For help, contact [hello@etchv.com](mailto:hello@etchv.com) with the request ID
and HTTP status. Do not send your API key.

Storage upload errors are recorded separately from watermarking errors. A failed
cloud upload does not invalidate an already verified Etchv asset or consume a
second credit. See [storage retry and error codes](/docs/storage).
