Both modes use the same processing, verification and credit rules. Choose how
your application receives the result.

## Choose an endpoint

| Mode | What happens |
| --- | --- |
| **Sync** · standard endpoint | Waits for the result; returns `202` if watermarking or video detection continues beyond 20 seconds |
| **Async** · append `/async` | Returns a `202` receipt after upload validation and durable acceptance. Poll or use a webhook |

Image and PDF sync detection return JSON directly without job continuation.
Validation, upload and download time add to processing time; async acceptance
still waits for validation and storage of the upload.

<Details title="All six endpoint pairs">

| Operation | Synchronous endpoint |
| --- | --- |
| Embed image | `POST /watermarks/images` |
| Detect image | `POST /watermarks/images/detect` |
| Embed PDF | `POST /watermarks/documents` |
| Detect PDF | `POST /watermarks/documents/detect` |
| Embed video | `POST /watermarks/videos` |
| Detect video | `POST /watermarks/videos/detect` |

Append `/async` to any endpoint above. There is no `/sync` suffix.
Use `watermarks:embed` or `watermarks:detect` as appropriate. Fields, format limits
and credit prices are the same in either mode.

</Details>

## Watermark a file synchronously

```sh
curl --fail-with-body https://api.etchv.com/watermarks/documents \
  -H "X-API-Key: $ETCHV_API_KEY" \
  -H 'Idempotency-Key: document_delivery_001' \
  -F 'file=@document.pdf' \
  --form-string 'data={"delivery":"delivery_001"}' \
  -D response-headers.txt --output response-body
```

- **`200`:** save the file with its `Content-Disposition` filename and keep `X-Watermark-ID`.
- **`202`:** read the JSON receipt and collect `result_url`. Do not save this body as media.
- **Error:** invalid input, endpoint IDs or unavailable credits can prevent job acceptance.

SDK embed methods follow pending jobs automatically.

## Watermark a file asynchronously

Use `/watermarks/documents/async` with the same headers and fields. Save the receipt’s
`request_id`, `status_url` and `result_url`.

## <span id="if-a-synchronous-request-takes-longer" />Retrieve a pending result (either mode)

1. GET `status_url` with your API key. Follow `Retry-After`: 6 seconds on Trial/Launch, 2 seconds on other plans.
2. Keep waiting for `queued`, `running` or `retrying`.
3. On `succeeded`, GET `result_url`: embedding returns media; detection returns JSON.
4. On `failed`, record `request_id` and `error_code`. Reserved credits are refunded.

A successful detection may report `watermarked: false`.

## Receive an async webhook instead of polling

Create an enabled [webhook endpoint](/docs/api/webhooks), save its signing secret,
and add its ID to the async request:

```sh
curl "https://api.etchv.com/watermarks/images/async?webhook_id=$ETCHV_WEBHOOK_ID" \
  -H "X-API-Key: $ETCHV_API_KEY" \
  -H 'Idempotency-Key: image_delivery_001' \
  -F 'file=@image.png' \
  --form-string 'data={"delivery":"delivery_001"}'
```

Only the selected endpoint receives this job’s terminal event. Webhooks are optional.

## Retry safely

| Situation | Action |
| --- | --- |
| Timeout or lost response | Repeat the same file, data, operation and options with the same `Idempotency-Key` |
| Same key, changed input/options | `409`; use a new key for a new operation |
| Async replay | Returns a `202` receipt for the existing job, even if finished. Inspect its status |
| Terminal failure | Same-key replay returns the failure. Use a new key for an intentional new attempt |

Persist your key before uploading: 8–128 letters, digits, hyphens or underscores.
An accepted job continues after disconnection. Retries and result retrieval do
not create another charge or webhook event; use explicit webhook redelivery if needed.

<Details title="Processing guarantees and retention">

- Up to five processing attempts with backoff, using the original input and ID.
- Worker crashes recover after lease expiry. Image and PDF jobs have a 30-minute deadline; video jobs add 15 seconds per frame, up to 90 minutes. Expired jobs are finalized and refunded when workers recover.
- Verified output, asset records and credit settlement commit together. Failures refund reservations.
- Job results last **24 hours**; expired retrieval returns `410`. The idempotency key remains recorded.
- Etchv library downloads last **30 days**; selected customer buckets control output retention. Records remain until deleted. Detection creates no library assets.
- Encrypted processing copies become eligible for deletion after **7 days**. Job/billing metadata remain for accounting and replay protection; original embedding JSON is not retained.

</Details>

## Try either mode in the dashboard

In **Watermark media** or **Detect watermark**, select **Request mode**.
Sync follows continuation automatically. Async shows a receipt; use **Check result**
later or select a webhook. Copyable examples follow your chosen mode.

## SDKs

Regular methods wait; submission methods return a receipt without polling.

| SDK | Submit embed / detection |
| --- | --- |
| [Node.js](/docs/sdks/node), [Java](/docs/sdks/java) | `submitEmbed` / `submitDetection` |
| [Python](/docs/sdks/python), [Rust](/docs/sdks/rust) | `submit_embed` / `submit_detection` |
| [Go](/docs/sdks/go) | `SubmitEmbed` / `SubmitDetection` |
| [C#](/docs/sdks/csharp) | `SubmitEmbedAsync` / `SubmitDetectionAsync` |

In C#, `Async` denotes nonblocking client I/O; **Submit** chooses a server-side job.

## Choose where results are stored

Embedding accepts `storage_destination_id` and optional `storage_key` queries.
Delivery retries reuse verified bytes without another charge. [Storage options](/docs/storage).
