Etchv storage is included by default, with 30-day downloads and no setup required.
If you prefer to store watermarked results in your own bucket instead, choose
this optional integration. Your bucket becomes the result’s storage location;
Etchv removes its temporary output after confirmed delivery. Asset records stay
in Etchv, and original uploads keep their existing 30-day Etchv retention.

Store verified images, PDFs and videos in an Azure Blob Storage container using
a container-scoped SAS token. Both private and already-public containers work.
Test the connection before using it for production. Etchv verifies the watermark
before delivery, preserves the result’s file format and MIME type, and retries
storage failures without another watermark operation or credit charge.

## 1. Create a container SAS

Use a dedicated container in a standard Azure public-cloud storage account.
Generate a SAS with:

- Resource: **container** (`sr=c`).
- Permissions: **read, create, write** (`sp=rcw`).
- Protocol: **HTTPS only** (`spr=https`).
- An expiry appropriate for your rotation policy.

A user-delegation SAS is preferred when available; its validity is bounded by the
delegation key. You will need to rotate expiring tokens. Do not supply an account
key, connection string, account-wide SAS, URL, or private endpoint.
[Microsoft documents SAS types and scope](https://learn.microsoft.com/en-us/azure/storage/common/storage-sas-overview).

## 2. Connect and verify

In [Dashboard storage](/dashboard/storage), choose **Azure Blob Storage**, then
enter the account name, container name, prefix and token. Supply only the query
string, optionally starting with `?`.

```json
{
  "name": "Production Azure",
  "provider": "azure",
  "account": "YOUR_STORAGE_ACCOUNT",
  "bucket": "watermarked-assets",
  "prefix": "etchv",
  "visibility": "private",
  "credentials": "sv=...&sr=c&sp=rcw&spr=https&se=...&sig=..."
}
```

Send this body to `POST /storage/destinations` with a `storage:write` admin key.
Then click **Test connection**, or `POST /storage/destinations/{id}/verify`. The
probe checks both write and read access. Tokens are encrypted and never returned
in API responses or download URLs.

## 3. Store and retrieve

Pass the destination ID to an [embedding request](/docs/storage). Etchv uploads a
block blob while preserving the original bytes and MIME type. Existing different
objects are never overwritten.

Private records include an `azure://account/container/key` reference. Use your
Azure credentials or Etchv’s authenticated delivery download endpoint. For a
container you have already made public, select public visibility to receive a
direct `https://account.blob.core.windows.net/container/key` URL without a SAS.
Etchv never changes anonymous-access settings.

A private download is proxied with server-side credentials; Etchv does not expose
the write-capable container SAS to the browser. When a token expires, pending
uploads retry. Replace `credentials`, verify the connection, then retry exhausted
deliveries while the temporary verified output is still available (up to 30 days).

## Renew access before expiry

The dashboard shows the access token's expiry. The API returns the same
non-secret timestamp as `credential_expires_at`; for a user-delegation SAS, this
is the earlier of the SAS expiry and its delegation-key expiry. Expired or
not-yet-valid tokens cannot be saved. An expired destination cannot be selected
for a new request until you replace its token and test the connection again.
Existing Azure files remain in your container, but authenticated Etchv downloads
also need a valid token.

User-delegation tokens last at most seven days. Automate renewal through your
own Azure identity and `PATCH /storage/destinations/{id}`, or renew manually in
**Storage**, then **Details**, then **Replace credentials**. Saving a replacement requires a
new connection check. Etchv does not silently extend Azure permissions.

To generate a token with Azure CLI after signing in with an authorized identity:

```bash
az storage container generate-sas \
  --account-name YOUR_STORAGE_ACCOUNT \
  --name watermarked-assets \
  --auth-mode login --as-user \
  --permissions rcw --https-only \
  --expiry YOUR_UTC_EXPIRY --output tsv
```

The identity needs blob read/write access on the container and permission to
request a delegation key on the storage account. A container-scoped custom role
plus **Storage Blob Delegator** on that account avoids granting general storage
administration. Keep the generated token out of logs and source control.
See Microsoft's [user-delegation SAS guide](https://learn.microsoft.com/en-us/azure/storage/blobs/storage-blob-user-delegation-sas-create-cli)
for role assignment and expiry details. Account-key authentication can remain
disabled when using user-delegation tokens.

GitHub OIDC can automate this token generation in your own integration. Etchv's
Azure connection still uses the scoped SAS you supply; direct Azure workload
identity authentication in the Etchv API is not currently offered.
